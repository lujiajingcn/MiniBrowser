## STUN 报错排查（npm start 时的 socket_manager.cc 噪音）
- 现象：`npm start` 后控制台刷 `ERROR:socket_manager.cc(141) Failed to resolve address for stun.services.mozilla.com., errorcode: -105`（-105 = ERR_NAME_NOT_RESOLVED）。
- 结论：**无害噪音，应用本身正常启动**。这是 Chromium WebRTC 网络层在解析 STUN 服务器时 DNS 失败，来自某个正在打开的网页（很可能是 `restoreSession` 恢复的标签页里用了 WebRTC 的站点），不是 MiniBrowser 代码 bug。
- 证据：grep 项目自有代码（main/renderer/preload/webview-preload/index.html/styles.css）**零 WebRTC 使用**；受控实验里 `new RTCPeerConnection({iceServers:[{urls:'stun:stun.services.mozilla.com'}]})` 会触发，但沙箱无显示环境不一定打印该日志行。
- **重要坑**：想用 `app.commandLine.appendSwitch('disable-features','WebRtc')` 关掉 WebRTC —— **在 Electron 31 无效**。受控实验验证：加该开关后渲染进程 `typeof RTCPeerConnection` 仍为 `function` 且可 `constructed`。Electron 无干净的 webPreferences 开关能禁用 WebRTC；强行剥离 `RTCPeerConnection` 会破坏视频会议/语音等实时站点。
- 处理建议：此类报错默认"保持现状"，仅影响该网页的实时通信能力，不影响普通浏览。若要消除噪音，优先定位并关闭触发 WebRTC 的那个标签页，而非全局禁用 WebRTC。

## ffmpeg 下载管线 端到端验证（补完）
- **环境前提**：本机 `ffmpeg` 在 PATH（`D:\ffmpeg\ffmpeg.exe`，ffmpeg 8.1.2）。直连本地 small.mp4 转封装 0.55s 出 2290B 有效 MP4；small.m3u8→small0.ts 经 `-c copy` 转封装出有效 MP4。
- **诊断监听坑（仅诊断侧）**：第一版后台 electron 诊断用 `win.webContents.on('mb-download', ...)` 在主进程监听，永远收不到事件——因为 `webContents.send()` 是发给**渲染进程** `ipcRenderer` 的，主进程 EventEmitter 收不到自己发出的这条消息。改为**包住 `win.webContents.send` 本身**捕获，等价观察渲染侧收到的事件。另：`session.defaultSession.resolveProxy(裸Windows路径)` 实测返回 `DIRECT` 不挂死（之前怀疑它挂死是误判）。
- **致命真实 bug（已修）**：`buildFfmpegArgs` 把 `-headers` 放在 `-i <url>` **之前**（当初当全局选项塞进 globalOpts）。但 `-headers`(及 `-http_proxy`) 是「输入 URL 相关的 demuxer 选项」，必须放在对应 `-i` **之后**，否则 ffmpeg 报 `Option headers not found` 并以退出码 2880417800 中断（= 真实的 `interrupted`，且**所有下载在正式环境都会失败**，不只是诊断）。
  - 修复：`video-ffmpeg.js` 改为 `['-y','-i',url, '-headers', ..., (proxy?'-http_proxy',...), '-c','copy','-bsf:a','aac_adtstoasc', outPath]`。纯 node 复现 `test-spawn.js` 验证 direct/hls 均 exit 0 且落盘有效 MP4；`test-video-logic.js` 加回归断言 `a1.indexOf('-headers') > a1.indexOf('-i')`。
- **最终结果（真实 electron + 真实生产模块 video-download.js 后台跑）**：
  - direct(mp4)：`added → updated → done(completed)`，落盘 2290B，`ftyp`=MP4 ✓
  - hls(m3u8)：`added → updated → done(completed)`，落盘 2479B，`ftyp`=MP4 ✓（`updated` 进度事件也正常触发）
  - 管线全链路（spawn→进度解析→done→写盘）正式确认打通。
- **现状**：`npm test` = 45 断言全过（含 `-headers after -i` 回归）；`test-video-logic.js` 为持久化验证资产。临时诊断文件 `diag-download.js`/`test-spawn.js`/`dl-*.json|log`/`.tmp-dltest`/`.tmp-dlrun*` 已清理。
- 用户真机待办：用真实页面（如 cctvnews snow-book 链接）跑一次真实 HLS/直链下载，验证联网 + 代理（若机器走代理，ffmpeg 经 `resolveProxy` 注入 `-http_proxy` 必须）场景。

## 保存页面 💾 按钮「点击没反应」bug（已修）
- 现象：用户点工具栏 💾 无任何反应（菜单不弹出）。
- 根因：`renderer.js:289` 有一个 `document.addEventListener('click', (e) => { if (菜单可见 && 点击目标不在菜单内) hideContextMenu(); })` —— 本意是「点菜单外关闭右键菜单」。但 💾 是**左键 click** 触发：`savePageBtn` 的 click 监听器先 `showSavePageMenu()`（显示菜单 `remove('hidden')`），紧接着同一个 click **冒泡到 `document`**，此时菜单可见且按钮不在菜单内 → 立刻被 `hideContextMenu()` 关掉 = 菜单闪现即灭 = 用户感知「没反应」。右键/链接菜单用 `contextmenu` 事件触发，不会冒泡成 `click`，所以没这问题。
- 修复：`renderer.js` 的 `savePageBtn` click 监听改成 `(e) => { e.stopPropagation(); showSavePageMenu(savePageBtn); }`，阻断冒泡到 document 关闭逻辑。菜单弹出后点菜单项（在 `contextMenu` 内）不会被 document 监听关闭；点别处仍正常关闭；再点 💾 为「重新渲染同内容」（无害，非 toggle）。
- 验证：`npm run lint` 10 文件全过。`activeGuestId()`（929 行，优先 `getWebContentsId()` 降级 `getWebContents().id`）经此前真实 electron 诊断确认在真机可用，下载链路该层无隐患。
